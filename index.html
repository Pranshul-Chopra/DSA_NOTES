MODULE 1

Introduction to Databases & DBMS

L1

Introduction & Significance of RDBMS

A database is an organized collection of inter-related data that models some aspect of the real world. A Database Management System (DBMS) is software that manages and provides access to a database.

📌 DefinitionDBMS = a collection of interrelated data + a set of programs to access that data, with the goals of convenience and efficiency.

Where do we find databases?

  • Banking: customer info, accounts, loans, transactions
  • Airlines: reservations, schedules
  • Universities: registration, grades, courses
  • E-commerce: order tracking, recommendations
  • Healthcare: patient records, prescriptions
  • Telecom: call records, billing, prepaid balances
💡 Why RDBMS mattersNearly every app you use — banking app, college portal, Swiggy, Flipkart — runs on a relational database at its core. Understanding RDBMS is the foundation of backend software engineering.
L2

DBMS Concepts, Schema & Instance

📌 SchemaThe logical structure of the database — what tables exist, what columns they have, what types those columns are. Think of it as the blueprint of the database.
📌 InstanceThe actual data stored in the database at a particular moment in time. The schema is fixed; the instance changes every time data is inserted, updated, or deleted.
ConceptProgramming AnalogyExample
SchemaData type declaration (int x;)instructor(ID, name, dept_name, salary)
InstanceValue of variable at runtimeRow: (10101, "Srinivasan", "Comp.Sci.", 65000)

The three-level architecture of a DBMS:

  • External Level (View): What the user sees — customized views per user role.
  • Conceptual Level (Logical): The complete logical structure — all tables, constraints, relationships.
  • Internal Level (Physical): How data is stored on disk — indexes, file organization, storage blocks.
L3

Database System vs File System

Before DBMS, applications stored data in flat files. This caused serious problems:

ProblemFile SystemDBMS Solution
Data RedundancySame data duplicated in multiple filesCentralized storage, no duplication
InconsistencyUpdates in one file, missed in anotherSingle source of truth
IsolationData trapped in different formatsUnified access via SQL
AtomicityPower failure = partial write = corrupt dataTransactions ensure all-or-nothing
ConcurrencyTwo users write simultaneously = data raceConcurrency control protocols
SecurityFile-level permissions onlyFine-grained row/column access control
IntegrityConstraints buried in app codeConstraints declared in schema (CHECK, FK)
💡 Real-World ExampleImagine a bank using text files. If you transfer ₹5000: step 1 deducts from your file, step 2 adds to recipient's file. Power cuts between steps → ₹5000 vanishes. A DBMS wraps both steps in a transaction — either both happen or neither does.
L4

Data Models & Schema Architecture

A data model is a collection of tools describing data, relationships, semantics, and constraints.

  • Relational Model: Data organized in tables (relations). Most widely used. SQL-based.
  • Entity-Relationship (ER) Model: Conceptual design tool — entities, attributes, relationships.
  • Object-Oriented Model: Data as objects with methods. Used in specialized systems.
  • Semi-structured Model (XML/JSON): Flexible schema. Used in NoSQL / web APIs.
  • Hierarchical Model (legacy): Tree structure. IBM IMS. Predecessor to relational.
  • Network Model (legacy): Graph structure. CODASYL. More flexible than hierarchical.
🔑 Key InsightThe Relational Model (invented by E.F. Codd at IBM, 1970) revolutionized databases by separating logical data structure from physical storage — programmers no longer had to care about how data was stored on disk.
L5

Data Independence, DB Languages & Interfaces

📌 Physical Data IndependenceAbility to change the physical schema (how data is stored) without changing the logical schema. You can add/change indexes, reorganize files on disk, and applications keep working.
📌 Logical Data IndependenceAbility to change the logical schema (add/remove tables or columns) without changing the external views/applications. Harder to achieve than physical independence.

Database Languages:

  • DDL (Data Definition Language): CREATE TABLE, ALTER, DROP — defines schema.
  • DML (Data Manipulation Language): SELECT, INSERT, UPDATE, DELETE — manipulates data.
  • DCL (Data Control Language): GRANT, REVOKE — controls access.
  • TCL (Transaction Control Language): COMMIT, ROLLBACK — manages transactions.
-- DDL example
CREATE TABLE student (
  ID       VARCHAR(5),
  name     VARCHAR(20) NOT NULL,
  dept_name VARCHAR(20),
  tot_cred  NUMERIC(3,0),
  PRIMARY KEY (ID)
);

-- DML example
SELECT name FROM student WHERE dept_name = 'Comp. Sci.';

Database Design Using the E-R Model

L7

ER Model Concepts: Entities, Attributes, Relationships

📌 EntityA "thing" or "object" in the real world that is distinguishable from other objects. E.g., a specific student (Amit, Roll 101) or a specific course (DBMS, CS201).
📌 Entity SetA set of all entities of the same type sharing the same properties. E.g., Student (all students), Course (all courses).

Types of Attributes:

  • Simple: Cannot be divided further. E.g., age, roll_no.
  • Composite: Can be divided into sub-parts. E.g., Name → (FirstName, LastName), Address → (Street, City, Pin).
  • Single-valued: One value per entity. E.g., roll_no.
  • Multi-valued: Multiple values per entity. E.g., phone_numbers. Shown with double ellipse in ER diagram.
  • Derived: Computed from another attribute. E.g., age derived from date_of_birth. Shown with dashed ellipse.
  • Null: Attribute has no value for some entity. E.g., middle_name.
📌 RelationshipAn association between two or more entities. E.g., student enrolls in course; instructor teaches course.

ER Diagram Notation:

SymbolRepresents
RectangleEntity Set
EllipseAttribute
Double EllipseMulti-valued Attribute
Dashed EllipseDerived Attribute
DiamondRelationship Set
Double RectangleWeak Entity Set
UnderlinePrimary Key Attribute
L8

Relationship Constraints

Mapping Cardinalities — how many entities on one side can be associated with entities on the other side:

TypeMeaningExample
One-to-One (1:1)One entity in A ↔ at most one in BPerson ↔ Passport
One-to-Many (1:N)One entity in A ↔ many in BDepartment → Instructor
Many-to-One (N:1)Many in A ↔ one in BInstructor → Department
Many-to-Many (M:N)Many in A ↔ many in BStudent ↔ Course

Participation Constraints:

  • Total participation (double line): Every entity in the set must participate in at least one relationship. E.g., every loan must be associated with a customer.
  • Partial participation (single line): Some entities may not participate. E.g., not every instructor is an advisor.
💡 Crow's Foot NotationIn modern tools (like MySQL Workbench, ERD tools), you'll see crow's foot symbols (|— one, >— many, ||— exactly one, O— zero) instead of lines/numbers. Same concept, different notation.
L9

ER Diagram Examples

Classic University ER Example:

  • Entity sets: Student, Instructor, Course, Department, Section
  • Relationships: takes (Student–Section, M:N), teaches (Instructor–Section, 1:N), advisor (Student–Instructor, M:1), dept_of (Instructor–Department, N:1)

Weak Entity Sets: An entity set that does not have a primary key of its own and depends on a strong (identifying) entity for its existence.

  • Example: Section depends on Course. Sec_id alone (like "1", "2") isn't unique globally — it needs course_id to be meaningful.
  • The partial key of the weak entity is called a discriminator.
  • Shown with a double rectangle (weak entity) and double diamond (identifying relationship).
L10

Generalization, Specialization & Aggregation (EER)

📌 GeneralizationBottom-up: combining two or more lower-level entity sets into a single higher-level entity set. E.g., Car and Truck → Vehicle.
📌 SpecializationTop-down: taking a higher-level entity set and creating distinct lower-level sub-entity sets based on distinguishing characteristics. E.g., Person → Student, Instructor, Staff.

Both use an ISA triangle (is-a hierarchy) in the EER diagram.

Constraints on Specialization:

  • Disjoint: An entity can belong to only one lower-level set. (marked "d")
  • Overlapping: An entity can belong to more than one lower-level set. (marked "o")
  • Total: Every higher-level entity must belong to at least one lower-level set. (double line)
  • Partial: Some higher-level entities may not belong to any lower-level set. (single line)
📌 AggregationTreating a relationship as a higher-level entity so that it can participate in another relationship. Used when a relationship needs to be related to another entity.

Example: Project is managed by an employee through a relationship, and that management relationship itself has an evaluation_date. The "manages" relationship is aggregated into a box and linked to evaluation.
L11

Transforming ER Diagram into Relational Tables

Mapping rules to convert an ER diagram to a relational schema:

  1. Strong Entity Set: Becomes a table with all its simple attributes. Composite attributes are flattened. Multi-valued attributes create a separate table.
  2. Weak Entity Set: Becomes a table including the primary key of the identifying entity + its own discriminator attributes.
  3. 1:N Relationship: Add the primary key of the "1" side as a foreign key on the "N" side table.
  4. M:N Relationship: Create a new separate table containing the primary keys of both entities as foreign keys (this forms the composite primary key).
  5. 1:1 Relationship: Can merge into one table, or add FK to either side.
  6. ISA (Specialization): Option 1: separate table per level. Option 2: single table with null values. Option 3: one table per leaf entity (includes all inherited attributes).
💡 Example – Student enrolls in Course (M:N) 
-- Two entity tables:
Student(s_id, name, dept)
Course(c_id, title, credits)

-- Junction table for M:N:
Enrollment(s_id, c_id, grade)
  -- s_id → FK references Student
  -- c_id → FK references Course
  -- (s_id, c_id) → composite PK

Relational Data Model

L12

Domains, Tuples, Attributes, Relations & Keys

📌 Core Terminology
  • Relation: A table with rows and columns. Mathematically, a subset of a Cartesian product of domains.
  • Tuple: A single row in a relation. Represents one record/entity.
  • Attribute: A column in a relation. Each attribute has a domain (set of allowed values).
  • Domain: The set of valid values for an attribute. E.g., domain of dept_name = {"CS", "EE", "Music", ...}
  • Degree: Number of attributes (columns) in a relation.
  • Cardinality: Number of tuples (rows) in a relation.

Properties of Relations:

  • No! two tuples are identical (relations are sets).
  • Tuple order is irrelevant.
  • Attribute order within a tuple is irrelevant (by name, not position).
  • All attribute values are atomic (1NF requirement).
  • NULL is a special marker meaning "unknown" or "not applicable."

Types of Keys:

Key TypeDefinitionExample
Super KeySet of attributes that uniquely identifies each tuple{ID}, {ID, name}, {ID, name, salary}
Candidate KeyMinimal super key (no redundant attributes){ID} only (removing any attr breaks uniqueness)
Primary KeyChosen candidate key — cannot be NULLID in instructor table
Foreign KeyAttribute that references primary key of another tabledept_name in instructor → department.dept_name
L13

Relational Database, Schemas & Integrity Constraints

Integrity Constraints ensure the data in a database is accurate and consistent:

  1. Domain Constraint: Each attribute value must belong to its defined domain. E.g., salary must be numeric, not a string.
  2. Key Constraint: No two tuples can have the same primary key value. Primary key ≠ NULL.
  3. Entity Integrity: The primary key of any tuple must not be NULL.
  4. Referential Integrity: A foreign key value must either match a primary key in the referenced table OR be NULL. No dangling references.
⚠️ Referential Integrity ExampleIf instructor.dept_name = 'Physics', then there must be a tuple in department with dept_name = 'Physics'. You can't have an instructor belonging to a department that doesn't exist.
MODULE 4

Relational Algebra

L14

Relational Algebra Operators – Unary, Binary, Set Operations

📌 What is Relational Algebra?A procedural query language that consists of a set of operations that take one or two relations as input and produce a new relation as output. It is closed — every operation produces a relation, so operations can be chained/nested.

1. SELECT (σ) — Filter Rows

Selects tuples that satisfy a given predicate. Works like the SQL WHERE clause.

σpredicate(relation)
-- Find instructors in Physics dept
σ dept_name = "Physics" (instructor)

-- Find instructors in Physics with salary > 90000
σ dept_name="Physics" ∧ salary > 90000 (instructor)

2. PROJECT (Π) — Filter Columns

Returns the relation with only the specified attributes. Removes duplicates (set semantics).

ΠA1, A2, ..., Ak(relation)
-- Show only ID, name, salary of instructors
Π ID, name, salary (instructor)

3. RENAME (ρ) — Rename Relation/Attributes

ρnew_name(relation) or ρnew_name(A1, A2...)(relation)

4. UNION (∪) — Combine Two Relations

Returns all tuples in either relation. Requires both relations to be union compatible (same number and type of attributes).

-- Courses offered in Fall 2009 OR Spring 2010
Π course_id (σ semester="Fall" ∧ year=2009 (section))
  ∪
Π course_id (σ semester="Spring" ∧ year=2010 (section))

5. SET DIFFERENCE (−) — In One But Not Other

-- Courses in Fall 2009 but NOT in Spring 2010
Π course_id (σ semester="Fall" ∧ year=2009 (section))
  −
Π course_id (σ semester="Spring" ∧ year=2010 (section))

6. CARTESIAN PRODUCT (×) — All Combinations

Combines every tuple from relation r with every tuple from relation s. If r has m tuples and s has n tuples, result has m×n tuples.

instructor × department  -- every instructor paired with every department
💡 Composition of OperationsThe power of relational algebra is composing operations. To find names of Physics instructors:
Π name (σ dept_name="Physics" (instructor))
Inner operation runs first: σ filters rows, then Π picks columns.
L15

Relational Algebra – Binary Operations & Joins

7. SET INTERSECTION (∩) — Tuples in BOTH relations (derived: r ∩ s = r − (r − s))

-- Courses offered in BOTH Fall 2009 AND Spring 2010
Π course_id (σ semester="Fall" ∧ year=2009 (section))
  ∩
Π course_id (σ semester="Spring" ∧ year=2010 (section))

8. NATURAL JOIN (⋈) — Join on common attribute(s), keep one copy

r ⋈ s

Automatically matches tuples with the same values on all common attributes. Retains only one copy of the shared attribute.

instructor ⋈ department
-- Joins on dept_name (common attribute)
-- Gives each instructor with their department building & budget

9. THETA JOIN (⋈θ) — Join on any condition

r ⋈θ s = σθ(r × s)

10. OUTER JOINS — Preserve unmatched tuples

TypeSymbolPreserves
Left Outer Joinr ⟕ sAll tuples from r; NULL fills missing s columns
Right Outer Joinr ⟖ sAll tuples from s; NULL fills missing r columns
Full Outer Joinr ⟗ sAll tuples from both; NULL fills missing either side

11. DIVISION (÷) — "For all" queries

r ÷ s

Returns tuples from r that match all tuples in s. Classic use: "Find students who have taken all courses offered by CS dept."

12. AGGREGATE FUNCTIONS (𝒢)

Extended operations not expressible with basic relational algebra:

G1,G2,...,Gn𝒢F1(A1), F2(A2),...,Fm(Am)(E)
  • G1...Gn = grouping attributes (like GROUP BY in SQL)
  • F1...Fm = aggregate functions: sum, avg, count, min, max
-- Sum of all instructor salaries
𝒢 sum(salary) (instructor)

-- Average salary per department
dept_name 𝒢 avg(salary) (instructor)

-- Count distinct instructors teaching in Spring 2010
𝒢 count-distinct(ID) (σ semester="Spring" ∧ year=2010 (teaches))
MODULE 5

SQL — Structured Query Language

L16

Basic SQL, DDL, DML, DCL & Views

SQL (Structured Query Language) is the standard language for relational databases. Originally called SEQUEL, developed at IBM in the 1970s.

DDL — Data Definition Language

-- Create a table
CREATE TABLE instructor (
  ID        CHAR(5),
  name      VARCHAR(20) NOT NULL,
  dept_name VARCHAR(20),
  salary    NUMERIC(8,2),
  PRIMARY KEY (ID),
  FOREIGN KEY (dept_name) REFERENCES department(dept_name)
);

-- Drop a table
DROP TABLE instructor;

-- Alter: add a column
ALTER TABLE instructor ADD COLUMN email VARCHAR(50);

-- Alter: drop a column
ALTER TABLE instructor DROP COLUMN email;

DML — Data Manipulation Language

-- SELECT: basic query structure
SELECT name, salary
FROM instructor
WHERE dept_name = 'Comp. Sci.' AND salary > 70000
ORDER BY salary DESC;

-- INSERT
INSERT INTO instructor VALUES ('10111', 'Nirupam', 'CS', 75000);

-- UPDATE
UPDATE instructor SET salary = salary * 1.05
WHERE dept_name = 'Comp. Sci.';

-- DELETE
DELETE FROM instructor WHERE dept_name = 'Finance';

VIEWS — Virtual Tables

-- Create a view
CREATE VIEW faculty AS
  SELECT ID, name, dept_name
  FROM instructor;

-- Query the view like a table
SELECT name FROM faculty WHERE dept_name = 'Physics';
💡 Why Views?Views provide logical data independence — the underlying table can change, but as long as the view still computes the same result, apps keep working. They also implement security by hiding sensitive columns like salary.

Additional SELECT Clauses:

-- AS: rename in output
SELECT name AS instructor_name, salary * 12 AS annual_salary
FROM instructor;

-- DISTINCT: remove duplicates
SELECT DISTINCT dept_name FROM instructor;

-- LIKE: pattern matching
SELECT name FROM instructor WHERE name LIKE 'S%';  -- starts with S
SELECT name FROM instructor WHERE name LIKE '__a%'; -- 3rd char is 'a'

-- NULL checks
SELECT name FROM instructor WHERE salary IS NULL;
SELECT name FROM instructor WHERE salary IS NOT NULL;
L17

SQL Joins

Joins combine rows from two or more tables based on a related column.

-- INNER JOIN (most common): only matching rows
SELECT s.name, t.course_id
FROM student s
INNER JOIN takes t ON s.ID = t.ID;

-- Same using NATURAL JOIN (auto-matches common columns)
SELECT name, course_id
FROM student NATURAL JOIN takes;

-- LEFT OUTER JOIN: all rows from left, NULL for non-matches on right
SELECT s.name, t.course_id
FROM student s LEFT OUTER JOIN takes t ON s.ID = t.ID;
-- Shows students even if they haven't taken any course

-- RIGHT OUTER JOIN
SELECT s.name, t.course_id
FROM student s RIGHT OUTER JOIN takes t ON s.ID = t.ID;

-- FULL OUTER JOIN: all rows from both sides
SELECT s.name, t.course_id
FROM student s FULL OUTER JOIN takes t ON s.ID = t.ID;
💡 INNER vs OUTER – Key DifferenceINNER JOIN: only rows that match on both sides. OUTER JOIN: includes unmatched rows too, filling missing columns with NULL. Most real applications use inner joins for data retrieval and outer joins for reporting/analysis.
L18

SQL Sub-queries

A sub-query (nested query) is a SELECT statement inside another SQL statement.

-- Sub-query in WHERE: find instructors earning more than avg salary
SELECT name FROM instructor
WHERE salary > (SELECT AVG(salary) FROM instructor);

-- IN sub-query: find students who took a course in Fall 2009
SELECT DISTINCT ID, name FROM student
WHERE ID IN (
  SELECT ID FROM takes
  WHERE semester = 'Fall' AND year = 2009
);

-- NOT IN: students who did NOT take any CS course
SELECT name FROM student
WHERE ID NOT IN (
  SELECT s.ID FROM takes t
  JOIN course c ON t.course_id = c.course_id
  WHERE c.dept_name = 'Comp. Sci.'
);

-- EXISTS: find courses with at least one student enrolled
SELECT course_id FROM course c
WHERE EXISTS (
  SELECT 1 FROM takes t WHERE t.course_id = c.course_id
);

-- Scalar sub-query: in SELECT list
SELECT name, (SELECT COUNT(*) FROM takes t WHERE t.ID = i.ID) AS course_count
FROM instructor i;
L19

SQL Aggregate Operations & Cursors

Aggregate Functions operate on a set of values and return a single value:

-- Basic aggregates
SELECT COUNT(*) AS total_instructors FROM instructor;
SELECT AVG(salary) AS avg_salary FROM instructor;
SELECT SUM(salary) AS total_payroll FROM instructor;
SELECT MAX(salary) AS highest_salary FROM instructor;
SELECT MIN(salary) AS lowest_salary FROM instructor;

-- COUNT DISTINCT
SELECT COUNT(DISTINCT dept_name) AS num_departments FROM instructor;

-- GROUP BY: compute aggregate per group
SELECT dept_name, AVG(salary) AS avg_salary
FROM instructor
GROUP BY dept_name;

-- HAVING: filter on aggregated results (like WHERE but for groups)
SELECT dept_name, AVG(salary) AS avg_salary
FROM instructor
GROUP BY dept_name
HAVING AVG(salary) > 75000;

-- Full example: departments with >2 instructors, showing count & avg salary
SELECT dept_name, COUNT(*) AS num_instructors, AVG(salary) AS avg_salary
FROM instructor
GROUP BY dept_name
HAVING COUNT(*) > 2
ORDER BY avg_salary DESC;
⚠️ WHERE vs HAVINGWHERE filters individual rows before grouping. HAVING filters groups after aggregation. You cannot use aggregate functions in WHERE; use HAVING instead.

Cursors allow row-by-row processing of query results (used in PL/SQL / stored procedures):

-- PL/SQL Cursor Example (Oracle)
DECLARE
  CURSOR c_instructor IS
    SELECT name, salary FROM instructor WHERE dept_name = 'CS';
  v_name    instructor.name%TYPE;
  v_salary  instructor.salary%TYPE;
BEGIN
  OPEN c_instructor;
  LOOP
    FETCH c_instructor INTO v_name, v_salary;
    EXIT WHEN c_instructor%NOTFOUND;
    DBMS_OUTPUT.PUT_LINE(v_name || ': ' || v_salary);
  END LOOP;
  CLOSE c_instructor;
END;
L20

Dynamic SQL

Dynamic SQL allows building and executing SQL statements at runtime — the SQL string is constructed dynamically (useful when table name or conditions aren't known at compile time).

-- PL/SQL Dynamic SQL using EXECUTE IMMEDIATE
DECLARE
  v_dept   VARCHAR2(20) := 'Physics';
  v_sql    VARCHAR2(200);
  v_count  NUMBER;
BEGIN
  v_sql := 'SELECT COUNT(*) FROM instructor WHERE dept_name = :1';
  EXECUTE IMMEDIATE v_sql INTO v_count USING v_dept;
  DBMS_OUTPUT.PUT_LINE('Count: ' || v_count);
END;

-- Dynamic table name example
DECLARE
  v_table VARCHAR2(50) := 'instructor';
  v_sql   VARCHAR2(200);
BEGIN
  v_sql := 'SELECT COUNT(*) FROM ' || v_table;
  EXECUTE IMMEDIATE v_sql;
END;
⚠️ SQL Injection RiskNever concatenate user input directly into dynamic SQL strings — this opens a SQL injection vulnerability. Always use bind variables (like :1 above) to safely pass user-provided values.
L21

Integrity Constraints in SQL

CREATE TABLE instructor (
  ID        CHAR(5)     PRIMARY KEY,
  name      VARCHAR(20) NOT NULL,
  dept_name VARCHAR(20),
  salary    NUMERIC(8,2) CHECK (salary > 0),  -- domain constraint
  FOREIGN KEY (dept_name) REFERENCES department(dept_name)
    ON DELETE SET NULL   -- if dept deleted, set to NULL
    ON UPDATE CASCADE    -- if dept_name changes, propagate here
);

-- Unique constraint (candidate key)
CREATE TABLE course (
  course_id CHAR(7) PRIMARY KEY,
  title     VARCHAR(50) UNIQUE,   -- no two courses with same title
  credits   NUMERIC(2,0) CHECK (credits > 0 AND credits <= 4)
);

-- Assertion: a constraint across tables (rarely supported)
CREATE ASSERTION salary_check CHECK (
  NOT EXISTS (
    SELECT * FROM instructor i, department d
    WHERE i.dept_name = d.dept_name AND i.salary > d.budget
  )
);

UNIQUEColumn or table-levelNo duplicate values (allows NULL)
PRIMARY KEYTable-levelUNIQUE + NOT NULL

L22

SQL Triggers

📌 TriggerA stored procedure that automatically executes (fires) in response to a specific event (INSERT, UPDATE, DELETE) on a specific table.
-- Oracle PL/SQL trigger: auto-update timestamp on salary change
CREATE OR REPLACE TRIGGER salary_update_log
AFTER UPDATE OF salary ON instructor
FOR EACH ROW
BEGIN
  INSERT INTO salary_audit(emp_id, old_sal, new_sal, changed_on)
  VALUES (:OLD.ID, :OLD.salary, :NEW.salary, SYSDATE);
END;

-- BEFORE trigger: prevent negative salary
CREATE OR REPLACE TRIGGER check_salary
BEFORE INSERT OR UPDATE ON instructor
FOR EACH ROW
BEGIN
  IF :NEW.salary < 0 THEN
    RAISE_APPLICATION_ERROR(-20001, 'Salary cannot be negative');
  END IF;
END;
PropertyOptions
TimingBEFORE, AFTER, INSTEAD OF
EventINSERT, UPDATE, DELETE (or combinations)
LevelROW level (FOR EACH ROW) or Statement level
References:OLD (previous values), :NEW (new values)
⚠️ Use Triggers CarefullyTriggers execute invisibly — they can cause unexpected behavior, cascading effects, and performance issues if overused. Prefer constraints when possible; use triggers only for logic that can't be expressed as constraints.

Database Design — Functional Dependencies & Normalization

L23

Armstrong's Axioms & Functional Dependencies

📌 Functional Dependency (FD)A constraint X → Y holds on relation R if for any two tuples t1, t2 in R: if t1[X] = t2[X] then t1[Y] = t2[Y]. Knowing the value of X uniquely determines the value of Y.

Types of Functional Dependencies:

TypeDefinitionExample
Trivial FDY ⊆ X (Y is subset of X){A,B} → A (always true)
Non-Trivial FDY ⊄ XStudentID → Name
Full FDY depends on complete X (composite key), not any proper subset{SID, CID} → Grade
Partial FDY depends on only part of composite keySID → StudentName (partial dependency on {SID,CID})
Transitive FDX→Y and Y→Z implies X→Z where Y is non-keyRollNo→Dept, Dept→DeptHead ⟹ RollNo→DeptHead

Armstrong's Axioms — complete and sound rules for deriving all FDs from a given set F:

  1. Reflexivity: If β ⊆ α, then α → β. (Trivial — X always determines a subset of itself)
  2. Augmentation: If α → β, then αγ → βγ. (Adding same attributes to both sides)
  3. Transitivity: If α → β and β → γ, then α → γ.

From these, we can derive additional rules:

  • Union: If α→β and α→γ, then α→βγ
  • Decomposition: If α→βγ, then α→β and α→γ
  • Pseudo-transitivity: If α→β and βγ→δ, then αγ→δ

Attribute Closure (α⁺) — the set of all attributes that α can determine:

-- Algorithm to compute (AG)+ given F = {A→B, A→C, CG→H, CG→I, B→H}
result = {A, G}
Apply A→B  → result = {A, B, G}
Apply A→C  → result = {A, B, C, G}
Apply CG→H → result = {A, B, C, G, H}
Apply CG→I → result = {A, B, C, G, H, I}
Apply B→H  → H already present
∴ (AG)+ = {A, B, C, G, H, I}

Finding Candidate Keys using Closure:

  1. Find attributes that never appear on the RHS of any FD — they must be in every candidate key.
  2. Compute the closure of those attributes.
  3. If closure = all attributes of R → those attributes form a candidate key.
  4. Check minimality: no proper subset should also give the full closure.
💡 Quick Rule for Candidate KeyAn attribute that never appears on the RHS of any FD cannot be derived from other attributes → it must be part of every candidate key. Start your search there!
L24

Canonical Cover, Lossless Join & Dependency Preservation

Canonical Cover (Fc) — a minimal, equivalent set of FDs with no redundancy:

  1. Step 1: Make all RHS single attributes (decompose: A→BC becomes A→B and A→C).
  2. Step 2: Remove extraneous attributes from LHS — for FD X→A, check if any attribute B in X can be removed (i.e., (X−B)+ already determines A).
  3. Step 3: Remove redundant FDs — check if each FD X→A can be derived from the remaining FDs (i.e., A ∈ X+ without that FD).
-- Example: E = {B→A, D→A, AB→D}
Step 1: All RHS already single. No decomposition needed.
Step 2: Check AB→D for extraneous attributes:
  - Remove A: B+ = {B,A,D} (via B→A then AB→D... actually B→D via B+)
    B+ with {B→A, D→A, B→D} = {B,A,D} ✓ → A is extraneous!
  - Replace AB→D with B→D
Step 3: Current set = {B→A, D→A, B→D}
  - B→A: without it, B+ = {B,D,A} via B→D, D→A → B→A redundant!
  - Remove B→A
Final Canonical Cover: Fc = {B→D, D→A}

Lossless-Join Decomposition — splitting a relation R into R1 and R2 such that we can reconstruct R exactly:

📌 Lossless DecompositionDecomposition of R into R1 and R2 is lossless if: R1 ∩ R2 → R1 OR R1 ∩ R2 → R2. The common attributes form a key of at least one of R1 or R2.
-- Example: R(A,B,C), F={A→B, B→C}
-- Decompose into R1(A,B) and R2(B,C)
-- R1 ∩ R2 = {B}
-- B → BC (since B→C), so B→R2 ✓ → Lossless!

-- Bad decomposition: R1(A,B) and R2(A,C)
-- R1 ∩ R2 = {A}
-- A → AB? Yes. → Lossless too!
-- But: R1(ID, name) and R2(name, street) would be LOSSY
-- because name→name is not a key (two people can have same name)

Dependency Preservation — all original FDs can still be checked using individual decomposed relations (without needing joins):

⚠️ Trade-offBCNF always achieves lossless decomposition but may NOT preserve all dependencies. 3NF always preserves dependencies and is lossless, but may have some redundancy. In practice, 3NF is often preferred because checking FDs after decomposition is much cheaper than joining tables.

Problems with NULL Values & Dangling Tuples

NULL values represent missing, unknown, or inapplicable information. They cause serious problems in many operations:

Problems with NULLs:

  • Comparisons: NULL = NULL is UNKNOWN (not TRUE). You can't use = with NULL; must use IS NULL.
  • Arithmetic: Any arithmetic with NULL returns NULL. 5 + NULL = NULL.
  • Aggregates: COUNT(*) counts NULLs, but SUM/AVG/MAX/MIN ignore them.
  • Three-valued logic: SQL uses TRUE, FALSE, UNKNOWN. A WHERE clause includes only TRUE rows.
ExpressionResult
NULL = NULLUNKNOWN
NULL > 5UNKNOWN
NULL AND TRUEUNKNOWN
NULL OR TRUETRUE
NOT NULLUNKNOWN
NULL IS NULLTRUE

Dangling Tuples — tuples that fail to join with any tuple in the other relation. In a natural/inner join, such tuples are simply lost from the result.

⚠️ ExampleIf a student has dept_name = NULL and you do student NATURAL JOIN department, that student disappears from the result — a dangling tuple! Use LEFT OUTER JOIN to preserve such tuples with NULLs filled in for missing department columns.

Why decomposition can create dangling tuples: If we decompose relation R into R1 and R2 based on a lossy decomposition, re-joining R1 ⋈ R2 may produce spurious tuples (extra wrong rows) not in original R. Lossless decomposition prevents this.

1NF and 2NF — First and Second Normal Form

Why Normalize? — Poor database design causes anomalies:

AnomalyProblemExample
Insertion AnomalyCan't insert new fact without inserting unrelated dataCan't add a new course unless a student enrolls
Deletion AnomalyDeleting one fact accidentally deletes anotherDeleting only student in OS course deletes the course info
Update AnomalySame data stored in multiple places — partial update = inconsistencyInstructor change must be updated in every row

First Normal Form (1NF)

📌 1NF RuleA relation is in 1NF if every attribute contains atomic (indivisible) values — no multi-valued attributes, no repeating groups, no sets/lists in any cell.
❌ Not in 1NF
Student_ID: 101, Name: Amit, Phone: {9876, 8765}
✅ 1NF Version
101 | Amit | 9876
101 | Amit | 8765

Second Normal Form (2NF)

📌 2NF RuleA relation is in 2NF if:
  1. It is already in 1NF, AND
  2. There is no partial dependency — every non-prime attribute must depend on the entire candidate key, not just part of it.
🔑 Partial dependency only matters when the candidate key is COMPOSITEIf the candidate key has only one attribute, partial dependency is impossible (you can't partially depend on a single attribute) → relation is automatically in 2NF if it's in 1NF.
-- Example: R(A, B, C, D, E, F), F = {A→C, B→DE, AB→F}
-- Step 1: Candidate Key?
--   A never appears on RHS, B never appears on RHS
--   Compute (AB)+ = {A,B,C,D,E,F} = all attributes → AB is CK!
-- Step 2: Prime attrs = {A, B}  |  Non-prime = {C, D, E, F}
-- Step 3: Check for partial deps:
--   A → C   : C depends on only A (part of AB) → PARTIAL DEP!
--   B → DE  : D,E depend on only B (part of AB) → PARTIAL DEP!
-- ∴ R is NOT in 2NF

-- Fix: Decompose!
-- R1(A, C)   [A→C]
-- R2(B, D, E) [B→DE]
-- R3(A, B, F) [AB→F] — the original key with the remaining attr
💡 Exam Shortcut for 2NF
  1. Find candidate key(s).
  2. Identify prime (in CK) and non-prime attributes.
  3. If CK is single attribute → automatically 2NF.
  4. If CK is composite → check every non-prime attr: does it depend on the full CK or just part?
  5. Any non-prime attr depending on part of CK = partial dep = NOT 2NF.
